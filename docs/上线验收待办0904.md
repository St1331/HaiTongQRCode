## 3. 总体执行顺序

必须优先完成阻断后续工作的基础环境，推荐顺序如下：

1. 建立 Git 基线和任务交付流程。
2. 安装 Docker，创建安全的本地或验收环境配置。
3. 启动 PostgreSQL，验证 migration、回滚和管理员种子。
4. 运行并补全 PostgreSQL 集成测试。
5. 运行并补全 Playwright E2E。
6. 验证完整容器栈和 HTTPS 部署。
7. 完成安全、性能和容量测试。
8. 完成加密备份与隔离恢复演练。
9. 完成真机打印扫码和业务 UAT。
10. 执行发布评审并归档证据。

每个编号应拆成独立任务、独立分支和独立 PR，不应把全部验收工作塞入一个提交。

## 5. T1：数据库与环境初始化

### 待办

1. 安装 Docker Desktop 或等效 Docker Engine，并确认：

   ```powershell
   docker version
   docker compose version
   ```

2. 从示例创建本地配置：

   ```powershell
   Copy-Item .env.example .env
   ```

3. 配置 `POSTGRES_PASSWORD`、`SESSION_HMAC_SECRET` 和 `IP_HMAC_SECRET`。两个 HMAC 密钥必须不同且至少 32 字符，不得提交真实值。
4. 启动 PostgreSQL：

   ```powershell
   docker compose up -d postgres
   docker compose ps
   docker compose logs postgres
   ```

5. 执行 migration：

   ```powershell
   pnpm.cmd --filter @haitong/api db:migrate
   ```

6. 使用环境变量创建超级管理员，然后立即清除当前 shell 中的密码变量。
7. 启动 API，分别验证 `/api/v1/health` 和 `/api/v1/ready`。
8. 重启 PostgreSQL 容器，确认数据卷中的数据仍然存在。

### 注意事项

- 开发库、测试库、性能库、恢复演练库和生产库必须分离。
- 禁止使用 TypeORM `synchronize: true`。
- 已在共享环境执行过的 migration 不得原地修改；结构变化必须新增 migration。
- `ready` 成功才证明数据库就绪，`health` 只能证明 API 进程存活。

### 完成标准

- PostgreSQL 17 健康运行。
- migration 能在空库成功执行。
- 超级管理员种子命令可重复安全执行。
- API 能连接数据库，容器重启后数据不丢失。

```dotenv

PUBLIC_BASE_URL=https://正式域名
COOKIE_SECURE=true
TRUST_PROXY_HOPS=实际可信代理层数
```

- 所有偏离 ADR 默认值的决定通过新 ADR 和对应 PR 落地。

## 15. 最终发布门禁

只有以下条件全部满足，才能标记首期完成并进入生产发布：

- `pnpm check`、真实 PostgreSQL 集成测试、关键 E2E 和生产构建全部通过。
- migration 在空库和适用升级场景验证通过。
- HTTPS、Cookie、CSRF、Origin、权限、公开 DTO 和限流检查通过。
- 没有未处理的阻断或高严重度缺陷。
- 性能达到批准的容量基线。
- 真实备份恢复演练成功。
- 真机打印扫码验收成功。
- 监控、告警、回滚和运维手册可用。
- 业务 UAT 完成并确认。
- PR、CI、测试报告、安全报告、性能报告、恢复报告和扫码记录均已归档。

## 16. 下一位开发者的首次操作清单

1. 阅读本文件及顶部列出的全部基线文档。
2. 执行 `git status`，保留所有用户已有改动。
3. 确认仓库是否仍无首个提交；若是，先与负责人确认初始基线提交方式，不要擅自丢弃文件。
4. 确认 Docker 是否可用，且根目录是否已有未提交的 `.env`。
5. 不输出 `.env` 的值，只检查所需键是否存在。
6. 从 T1 开始推进；数据库未就绪前，不要把 skipped 集成测试视为通过。
7. 每完成一个任务，更新本文对应状态、验证命令、结果日期和证据位置。
