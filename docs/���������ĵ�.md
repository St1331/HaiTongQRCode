# HaiTongQRcode 招标文件与合同二维码核验系统——开发基线文档

> 文档版本：1.0  
> 文档状态：已采纳开发基线  
> 适用范围：需求、设计、开发、测试、部署、运维与验收  
> 变更规则：范围、公开字段、核心技术、安全基线和数据模型的变更必须通过 ADR 与 Pull Request 记录。

## 1. 项目概述

### 1.1 建设目标

HaiTongQRcode 用于登记招标文件和合同的关键事实，并为每条登记记录生成唯一二维码。工作人员把二维码打印、粘贴或嵌入对应文件后，公众无需登录即可扫码核验该记录是否由企业登记、当前是否有效，以及纸质或电子文件上的关键字段是否与登记信息一致。

### 1.2 核心业务闭环

1. 管理员创建工作人员账号并分配角色。
2. 有权限的工作人员录入招标文件或合同信息，先保存为草稿。
3. 系统生成不可预测且唯一的公开查询令牌。
4. 工作人员确认内容后发布记录，下载带记录编号的二维码。
5. 公众扫码打开移动端核验页，对照文件编号、标题、主体、版本和日期等关键字段。
6. 工作人员修改、变更或作废记录时，原二维码继续展示该记录的最新状态。
7. 系统保存每次有效修改的历史快照和操作审计。

### 1.3 防伪能力边界

本系统证明“某份文件及其关键属性是否在企业系统中登记、登记版本和当前状态”，不等同于电子签章、CA 认证或司法意义上的原件鉴定。

二维码被复制到另一份文件后仍会指向真实记录，因此核验页必须提醒用户逐项比对编号、标题、主体、版本和日期。二维码只包含查询地址，不直接包含项目名称、合同金额、联系人或其他业务信息。

系统可登记原始电子文件的 SHA-256 摘要，以辅助确认电子文件内容是否变化；首期不上传、存储或提供原文件下载。

## 2. 范围与非目标

### 2.1 首期范围

- 管理员登录、退出、会话撤销和密码修改。
- 用户创建、禁用、启用、角色调整和管理员重置密码。
- `SUPER_ADMIN`、`EDITOR`、`VIEWER` 三类角色权限。
- 招标文件、合同两类登记记录的新增、编辑、详情、检索、分页和状态变更。
- 唯一公开查询令牌与二维码预览、PNG 下载和打印预览。
- 公众匿名核验页和公开查询接口。
- 历史版本、操作审计、并发修改保护。
- 登录防暴力破解、公开接口限流、CSRF/CORS/安全响应头和日志脱敏。
- 自动化测试、Docker Compose 部署、监控、备份、恢复和回滚说明。

### 2.2 首期非目标

- 原始 PDF、Word 或附件上传与下载。
- 电子签章、CA 认证、区块链存证或法律意义上的原件鉴定。
- 在线支付、短信、微信公众号、小程序和消息订阅。
- 企业统一身份认证、多因素认证和多租户 SaaS。
- 富文本公开备注；首期只允许纯文本。

非目标不得提前实现，但数据模型和模块边界不得明显阻碍后续扩展。

## 4. 业务规则

### 4.1 登记类型

- `TENDER_DOCUMENT`：招标文件。
- `CONTRACT`：合同。

两类记录共享编号、标题、登记主体、版本、日期、公开备注和状态。合同可填写相对方、金额展示文本、签订日期和有效期；招标文件可填写招标人、代理机构、项目类型和发布日期。

### 4.2 状态机

- `DRAFT`：草稿；公众不可查询。
- `ACTIVE`：有效；公众可查询。
- `CHANGED`：已变更；公众可查询并显示橙色文字与图标提示。
- `VOID`：已作废；公众可查询并显示红色文字与图标警示。

允许的转换：

```text
DRAFT   -> ACTIVE | VOID
ACTIVE  -> CHANGED | VOID
CHANGED -> ACTIVE | VOID
VOID    -> 不允许恢复
```

所有状态转换由服务端校验。转为 `CHANGED` 或 `VOID` 时变更原因必填，5～500 个字符；其他转换原因可选。确需恢复作废记录时必须创建新记录，并在公开备注或内部说明中引用原记录。

### 4.3 公开查询令牌

- 创建记录时一次性生成 192 bit 密码学安全随机值并使用 Base64URL 编码。
- 令牌不可由 UUID、数据库 ID、业务编号、时间戳或其他可枚举值推导。
- 数据库建立唯一约束；极低概率冲突时在有限次数内重新生成。
- 日常信息更新和状态变化不改变令牌，保证原二维码持续可用。
- 只有超级管理员可在疑似泄露时执行令牌轮换；轮换后旧二维码立即失效，操作必须二次确认并审计。
- 二维码内容固定为服务端配置的 `https://正式域名/v/{publicToken}`。

### 4.4 修改、版本和审计

- 所有影响公开展示的真实修改均创建“修改后完整公开快照”。无实际变化时不创建版本。
- 主记录修改、版本快照和审计日志必须位于同一数据库事务。
- 使用整数 `revision` 实现乐观锁；客户端编辑时提交读取到的 revision。
- revision 不一致返回 HTTP `409` 和稳定错误码 `DOCUMENT_CONFLICT`，不得覆盖他人修改。
- 审计日志只允许追加，业务应用不得更新或删除审计记录。
- 密码、会话令牌、Cookie、Authorization、CSRF 令牌和原始 IP 不得进入应用日志或审计摘要。
- 业务记录使用软删除；首期管理页面不提供删除入口。

## 5. 公开信息规则

公开接口使用显式 DTO 映射，禁止直接序列化数据库实体。

### 5.1 所有类型公开字段

- 登记类型、记录编号、标题、登记/签发主体。
- 当前状态、文件版本、关键业务日期。
- 最后更新时间、公开备注。
- 文件 SHA-256 摘要（仅在业务方主动登记时显示）。

### 5.2 类型专有公开字段

- 招标文件：招标人、代理机构、项目类型、发布日期。
- 合同：合同相对方、金额展示文本、签订日期、有效起止日期。

联系方式、内部备注、操作人员、数据库 ID、审计信息和系统元数据一律不公开。合同金额是否公开须在 P0 由业务方确认；未确认时默认不公开。

`ACTIVE`、`CHANGED`、`VOID` 返回公开 DTO；`DRAFT`、软删除、不存在和格式非法的令牌统一返回 `404`，避免泄露记录是否存在。

### 6.1 技术栈

| Monorepo   | pnpm workspace + Turborepo                            |

| 表单与校验 | React Hook Form + Zod                                 |

| 测试       | Vitest、Supertest、Playwright、独立 PostgreSQL 测试库 |
| 部署       | Docker Compose + Nginx                                |

使用开发时稳定版本并提交锁文件。生产环境禁止 `synchronize: true`。未经 ADR 不更换核心框架。

### 6.2 边界和部署

```text
手机/微信 ─ HTTPS ─ Nginx ─ Next.js ─ Express API ─ PostgreSQL
管理电脑 ─ HTTPS ─ Nginx ─ Next.js ─ Express API ─ PostgreSQL
```

- `web` 只负责页面、交互和调用 API，不直连数据库。
- `api` 负责认证、授权、业务规则、二维码、数据访问和审计。
- `shared` 只存放可安全共享的类型、枚举、Schema 和纯函数，不包含实体或秘密。
- Nginx 统一同源访问、HTTPS、安全头、请求体限制、超时和反向代理。
- API 只信任明确配置的代理层；不得无条件信任任意 `X-Forwarded-For`。

## 7. 数据模型基线

所有主键使用 UUID；时间点使用 `timestamptz` 并以 UTC 存储，业务日期使用 `date`，不做时区换算。页面按配置的业务时区显示时间点。

### 7.1 users

包括：`id`、规范化后唯一的 `username`、`display_name`、`password_hash`、`role`、`status`、`failed_login_count`、`locked_until`、`last_login_at`、`password_changed_at`、创建和更新时间。

### 7.2 auth_sessions

采用服务端不透明会话，不采用可长期独立使用的浏览器 JWT。表中保存会话令牌的 HMAC/SHA-256 派生值、用户、空闲过期时间、绝对过期时间、撤销时间和限长设备摘要；数据库不得保存可直接使用的明文会话令牌。

### 7.3 verification_records

主要字段：`id`、`record_type`、唯一 `public_token`、`record_number`、`title`、`issuer_name`、招标/合同类型专有字段、`document_version`、`status`、业务日期、可选 `file_sha256`、`public_remark`、内部说明、`revision`、创建/修改人、创建/更新时间和 `deleted_at`。

字段长度、空白规范化和类型专有必填规则必须同时落实在 Zod 与数据库约束中。建议基线：编号 1～100、标题 1～200、主体名称 1～200、版本 1～30、公开备注最多 1,000、内部说明最多 2,000 个字符。

编号首期默认不强制全局唯一，但对规范化编号和未删除记录建立部分索引；保存重复编号时向工作人员醒目提示。最终唯一性规则在 P0 冻结。

### 7.4 record_versions

包括：`id`、`record_id`、`version_no`、`snapshot jsonb`、`change_reason`、`changed_by` 和 `created_at`。建立 `UNIQUE(record_id, version_no)` 和外键。版本号在事务内加锁递增，必须大于零。

### 7.5 audit_logs

包括：`id`、可空 `actor_id`、动作、资源类型、可空资源 ID、脱敏摘要、请求 ID、可选 IP HMAC、限长 User-Agent 和创建时间。IP 使用带服务端密钥的 HMAC，不使用可直接字典反推的普通哈希。

所有外键、唯一约束、检查约束、删除策略和必要索引必须由 TypeORM migration 创建。

## 8. API 契约

API 前缀统一为 `/api/v1`；JSON 响应包含 `requestId`。生产环境不得返回堆栈、SQL、路径或内部异常原文。

### 8.1 认证与用户

```text
POST  /api/v1/auth/login
POST  /api/v1/auth/logout
GET   /api/v1/auth/me
POST  /api/v1/auth/change-password
GET   /api/v1/admin/users
POST  /api/v1/admin/users
PATCH /api/v1/admin/users/:id
POST  /api/v1/admin/users/:id/reset-password
```

### 8.2 登记管理

```text
GET   /api/v1/admin/records
POST  /api/v1/admin/records
GET   /api/v1/admin/records/:id
PATCH /api/v1/admin/records/:id
POST  /api/v1/admin/records/:id/status
POST  /api/v1/admin/records/:id/rotate-token
GET   /api/v1/admin/records/:id/versions
GET   /api/v1/admin/records/:id/qrcode
GET   /api/v1/admin/audit-logs
```

列表仅允许白名单排序字段，`page` 从 1 开始，默认 `pageSize=20`，最大 100。

### 8.3 公开接口

```text
GET /api/v1/public/records/:publicToken
```

成功响应设置短时缓存，基线为浏览器 `max-age=0`、共享缓存 `s-maxage=60`；每次修改、状态变化、软删除或令牌轮换均主动失效服务端缓存。未部署可可靠失效的共享缓存前不得启用长 TTL。

### 8.4 错误格式

```json
{
  "error": {
    "code": "RECORD_NOT_FOUND",
    "message": "未找到对应的登记信息",
    "details": null
  },
  "requestId": "req_xxx"
}
```

验证错误使用 `400`，未认证使用 `401`，无权限使用 `403`，不存在使用 `404`，并发冲突使用 `409`，限流使用 `429`。

## 9. 认证与安全基线

- Nginx 下 Web 与 API 同源部署；会话 Cookie 使用 `Secure`、`HttpOnly`、`SameSite=Lax` 和最小化 Path。
- 所有改变状态的请求验证 Origin，并使用 CSRF 令牌；CORS 默认关闭，确需跨源时仅允许显式白名单。
- 密码至少 12 个字符，允许密码管理器生成的长密码；使用 argon2id，参数经目标服务器基准测试确定。
- 连续 5 次登录失败锁定 15 分钟；成功登录后清零。按账号与来源组合限流，响应不泄露账号是否存在。
- 会话空闲 8 小时失效、最长 7 天；退出、禁用账号、重置密码后撤销相关会话。
- 登录、用户管理、状态变化、令牌轮换和拒绝的高风险操作均写审计日志。
- 请求体默认不超过 256 KiB；所有字符串限制长度；查询使用参数绑定；页面按文本渲染用户输入。
- 配置 Content-Security-Policy、HSTS、X-Content-Type-Options、Referrer-Policy 和 frame 限制。
- 秘密仅通过环境变量或密钥管理设施注入，不进入代码、镜像、日志、测试夹具或 Git 历史。
- 公开接口同时采用来源 IP HMAC 维度和令牌维度限流；具体阈值经压测确定并支持配置。

## 10. 页面和体验

### 10.1 管理端

```text
/admin/login
/admin/records
/admin/records/new
/admin/records/[id]
/admin/records/[id]/edit
/admin/audit-logs
/admin/users
```

列表支持类型、编号、标题、状态和日期范围筛选，条件写入 URL。页面必须包含明确的加载、空、错误、成功和重试状态。

表单前后端采用同一 Schema；防重复提交；离开未保存页面前提示；并发冲突不得静默覆盖。状态变化和令牌轮换使用二次确认。

二维码下载和打印预览必须同时展示记录类型、编号和标题，降低贴错风险。

### 10.2 公众核验页

路由：`/v/[publicToken]`

页面移动优先，显示企业核验标题、文字与图标形式的状态、公开字段、最后更新时间和“请与原文件逐项核对”的说明。必须覆盖有效、已变更、已作废、未找到、网络异常和维护状态，并支持键盘访问和 200% 文本缩放。

## 11. 工程与 GitHub 工作流

- 默认分支为 `main`，保持可构建、可测试、可部署。
- 每个开发任务开始前执行 `git switch main` 和 `git pull --ff-only`。
- 每个任务使用独立分支，如 `feat/P2-T1-express-bootstrap`、`fix/...` 或 `docs/...`。
- 一个任务对应至少一个清晰提交和一个 Pull Request；不得把多个阶段混在同一 PR。
- PR 标题包含任务编号；正文必须填写完成内容、主要文件、迁移影响、验证命令与结果、风险、已知限制和截图（如适用）。
- CI 必须通过 lint、typecheck、unit test 和 build；涉及 API/数据库/关键页面时增加相应集成或 E2E 测试。
- 合并优先使用 squash；合并后删除远端任务分支。未经用户明确授权，不直接向 `main` 推送功能开发。
- 锁文件必须提交；不得通过删除测试、降低断言、使用 `any` 或关闭安全约束让 CI 通过。

## 12. 分阶段开发计划

### P0：决策冻结

- P0-T1：确认正式域名、业务时区、编号唯一性、公开合同金额、代理机构配置方式、数据规模、数据与日志保存期限。
- P0-T2：建立 ADR，冻结认证方案、公开 DTO、缓存、备份和性能目标。

完成标准：未决项均有结论或显式默认值。

### P1：工程骨架

- P1-T1：建立 pnpm/Turborepo、Web/API/shared、严格 TypeScript、ESLint、格式化和统一脚本。
- P1-T2：建立 GitHub Actions，执行锁文件安装、lint、typecheck、unit test 和 build。
- P1-T3：建立 PostgreSQL Docker Compose、健康检查、持久化卷和环境变量示例。

### P2：API 与数据库基础

- P2-T1：Express 应用工厂、请求 ID、Pino、Helmet、请求体限制、统一错误和健康检查。
- P2-T2：TypeORM 数据源、基础 migration、测试库、迁移与回滚命令。
- P2-T3：幂等种子超级管理员命令，密码只从环境变量或交互输入取得。

### P3：认证、用户与授权

- P3-T1：登录、退出、不透明会话、锁定和会话撤销。
- P3-T2：认证、CSRF 与角色授权中间件及权限矩阵测试。
- P3-T3：用户创建、禁用、角色调整、密码修改和管理员重置密码。

### P4：登记记录领域

- P4-T1：实体、枚举、Schema、DTO、仓储、索引与令牌生成。
- P4-T2：创建、详情、首版快照和审计事务。
- P4-T3：带 revision 的编辑、版本快照和并发冲突。
- P4-T4：状态机、原因校验和审计。
- P4-T5：分页、排序、组合筛选和典型查询计划检查。

### P5：二维码与公众核验

- P5-T1：服务端固定 URL 二维码 PNG、文件名、打印尺寸和自动解码测试。
- P5-T2：公开 DTO、404 一致性、限流、缓存和失效测试。
- P5-T3：令牌轮换与旧令牌失效。
- P5-T4：微信、系统相机、其他扫码工具及 iOS/Android 真实打印扫码记录。

### P6：Web 页面

- P6-T1：登录、会话恢复、退出、管理布局和无权限页。
- P6-T2：列表、筛选、分页、状态与错误恢复。
- P6-T3：新建、编辑、状态转换和并发冲突提示。
- P6-T4：详情、历史、二维码预览/下载/打印。
- P6-T5：移动端公众核验页和无障碍验证。
- P6-T6：用户管理和审计日志页。

- P7-T2：结构化日志、指标、告警与运维手册。

- P7-T4：全量测试、安全检查、依赖检查、性能测试和用户验收。

## 13. 测试与发布门禁

### 13.1 测试层次

- 单元测试：状态机、权限、DTO 白名单、规范化、令牌/URL、日期和脱敏。
- 集成测试：使用独立 PostgreSQL，覆盖 migration、约束、事务、认证授权、版本与审计原子性。
- E2E：登录、建草稿、发布、下载二维码、公开核验、修改、变更、作废、Viewer 拒绝和会话过期。
- 专项测试：二维码自动解码、不同打印尺寸、倾斜/折痕/室内光线、多扫码工具和多移动系统。

测试自行准备并清理数据，不依赖执行顺序，不使用 SQLite 代替 PostgreSQL。

### 13.2 基线性能目标

在 10 万条登记记录、50 个后台账号、公开查询峰值 50 RPS 的基线负载下：公开 API P95 不高于 500 ms、错误率低于 1%，后台常用查询 P95 不高于 1 s。最终指标应根据生产服务器规格和实际峰值在 P0 修订。

### 13.3 发布阻断条件

以下任意一项不满足不得发布：

- lint、typecheck、单元测试、集成测试、关键 E2E 或 build 失败。
- 存在未处理的阻断或高严重程度缺陷。
- migration 未在空库和上一版本副本验证。
- HTTPS、Cookie、CSRF、CORS、权限或限流检查不合格。
- 正式配置含默认密码、真实秘密进入 Git 历史或日志泄露敏感字段。
- 备份恢复演练、真实打印扫码测试或关键业务冒烟测试未完成。

## 14. 部署、监控、备份与回滚

- 基线可用性目标为月度 99.5%，计划维护窗口除外。
- API 健康、5xx 比例、P95 延迟、数据库连接、磁盘空间和备份结果需要监控；连续异常触发告警。
- 默认每日全量备份，保留 30 天，并保存至少一份加密异地副本；审计和业务数据保存期限由业务方在 P0 确认。
- 初始目标 RPO 为 24 小时、RTO 为 4 小时；若业务要求更高，必须调整备份频率和部署规格。
- 每次正式发布前备份数据库并验证可读，在预发布运行 migration 和冒烟测试。
- 数据库采用“扩展—迁移—收缩”，优先保证应用版本可回退；已在共享环境执行的 migration 不得原地修改。
- 至少完成一次隔离环境真实恢复并抽样核对用户、记录、版本和审计数据，不能只证明备份文件存在。

## 15. 完成标准

项目同时满足以下条件才算首期完成：

- 招标文件和合同从录入、发布、二维码生成到公众扫码核验的闭环通过验收。
- 二维码与记录一一对应，信息更新后原码继续有效，令牌轮换行为符合规则。
- 状态、权限、历史、审计、并发保护和公开字段白名单有自动化验证。
- 常见扫码方式、iOS/Android、打印场景和移动端可访问性通过验证。
- 全量 CI、构建、安全检查和性能基线通过。
- 部署、监控、备份、恢复、回滚和运维文档齐全，真实恢复演练成功。
- 无阻断或高严重程度已知缺陷。

## 16. P0 待业务方确认事项

1. 正式域名和 HTTPS 证书由谁维护。
2. 记录编号是否允许重复；若允许，人工判重依据是什么。
3. 合同金额是否属于公开核验字段。
4. 招标代理机构是否固定，项目类型是否固定下拉。
5. 作废记录是否永久允许公众核验；默认永久可见作废警示。
6. 文件 SHA-256 摘要是否首期启用，以及由谁计算和录入。
7. 业务时区；默认 `Asia/Shanghai`。
8. 业务数据、历史版本和审计日志保存年限。
9. 预计记录总量、账号数、日扫码量和峰值 RPS。
10. RPO、RTO、可用性及性能目标是否接受本文默认值。
